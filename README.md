این مخزن **منبع حقیقت** است. مستندات `docs.payam-resan.com`، نمونه‌کدهای هر
زبان و سرور MCP همگی از همین‌جا مشتق می‌شوند. هیچ‌کدام نباید دستی با سرویس
هم‌گام شوند، چون در آن حالت هر تغییر API یعنی ده‌ها ویرایش پراکنده و
واگرایی خاموش.

## چیدمان

```
specs/
└── v3/
    ├── openapi.yaml              توصیف OpenAPI 3.1
    └── codes/
        ├── error-codes.yaml      مقادیر ErrorCode
        ├── status-codes.yaml     مقادیر StatusCode
        └── template-status.yaml  وضعیت تأیید قالب
scripts/
└── validate.py                   spec در برابر جدول‌ها
```

نسخه یک پوشه است، نه یک شاخه و نه یک تگ. نسخه‌های قدیمی‌تر سرویس هنوز فعال‌اند
و باید در کنار نسخهٔ جاری خوانده شوند، پس هر نسخه پوشهٔ خودش را می‌گیرد و
اعتبارسنج همه را با هم بررسی می‌کند. اضافه شدن یک نسخه یعنی یک پوشهٔ تازه و
هیچ تغییری در پوشه‌های موجود.

## چرا کدها جدا از spec

مقادیر `ErrorCode` و `StatusCode` در دو جا لازم‌اند: به‌عنوان `enum` در
اسکیمای پاسخ، و به‌عنوان جدولِ «این عدد یعنی چه» که مستندات، نمونه‌کدها و
سرور MCP نشان می‌دهند. یکی‌شان بدون دیگری کافی نیست، و نگه داشتن متن فارسی
داخل `description` یک enum عملاً غیرقابل مصرف است.

پس عددها در spec می‌مانند، متن‌ها در `codes/`، و
[`scripts/validate.py`](scripts/validate.py) شکست می‌خورد اگر این دو از هم
واگرا شوند.

## اجرا

دو بررسی مستقل، و هر دو باید سبز باشند.

**۱. سازگاری spec با جدول کدها** — تنها وابستگی `PyYAML` است.

```bash
python3 scripts/validate.py            # بررسی و گزارش
python3 scripts/validate.py --gaps     # فقط فهرست شکاف‌ها، برای پیگیری
python3 scripts/validate.py --strict   # هشدار هم شکست حساب می‌شود
```

**۲. اعتبار خود OpenAPI** — با Docker، بدون نصب چیزی.

```bash
docker run --rm -v "$PWD":/spec -w /spec redocly/cli lint specs/v3/openapi.yaml
```

قواعد خاموش‌شده و دلیلشان در [`redocly.yaml`](redocly.yaml) است.

## پوشش

هیچ شکاف بازی نمانده است. هر کدی که سرویس اعلام می‌کند نام، شرح، علت و
راهکار دارد، و هیچ‌کدام حدسی پر نشده‌اند.

| جدول | پوشش | چطور تأیید شد |
|---|---|---|
| کد خطا | ۲۰ کد موجود، هر کدام با دستهٔ `retry` | تیم سرویس |
| وضعیت پیامک | ۲۲ کد، `0` تا `21`، هر کدام با `disposition` | تیم سرویس، کد `8` با پاسخ زنده |
| وضعیت قالب | ۳ کد، هر سه با پاسخ زندهٔ `TokenList` سنجیده شد | مقایسهٔ پنل با API |

سه چیز که در فهرست عمومی پیشین نبود و اینجا مستند شده است:

- متد `GetInbox` و واریانت `POST` متد `SendTokenSingle`
- کدهای خطای `16` تا `20` و `100`، و کدهای وضعیت `18` تا `21`
- کد خطای `7` که حذف شده و دیگر برگردانده نمی‌شود

دو ناسازگاری هم عیناً ثبت شده‌اند، چون در خود سرویس‌اند و اصلاحشان اینجا
کد را از پاسخ واقعی جدا می‌کرد:

| ناسازگاری | جزئیات |
|---|---|
| غلط املایی | فیلد فرستنده در `GetInbox` نامش `Form` است، نه `From` |
| وضعیت قالب | پنل چهار حالت دارد و بین دو نوع رد شدن فرق می‌گذارد، ولی API هر دو را `3` برمی‌گرداند |

### آنچه مرجع تازه باید درست بگوید

فهرست عمومی قدیمی بازنشسته می‌شود و مرجع تازه
[`docs.payam-resan.com`](https://docs.payam-resan.com) است. این‌ها مواردی
است که صفحهٔ قدیمی غلط یا ناقص می‌گفت و مرجع تازه نباید تکرارشان کند:

| مورد | صفحهٔ قدیمی چه می‌گفت | درست چیست |
|---|---|---|
| کد ۶ | از تأیید تلفن همراه می‌گوید | `NoAuthntication`، احراز هویت حساب انجام نشده |
| کد ۷ | هنوز فهرست شده است | حذف شده، دیگر برگردانده نمی‌شود |
| کد ۱۳ | فقط فرمت شماره | سقف تعداد گیرنده را هم پوشش می‌دهد |
| کدهای ۱۶ تا ۲۰ و ۱۰۰ | اصلاً نیستند | وجود دارند و اینجا مستند شده‌اند |
| `SendTokenSingle` | `P1` تا `P3` | `p1` تا `p10` |
| متدها | ۹ متد | ۱۰ مسیر، شامل `GetInbox` |
| وضعیت پیامک ۱۷ | سقف روزانه و سقف API را قاطی می‌کرد | ۱۷ روزانه است، ۱۸ مخصوص API |
| وضعیت پیامک | فقط تا ۱۷ | تا ۲۱ |
| وضعیت‌های ۷، ۱۱ | معنایشان با آنچه سرویس می‌گوید فرق داشت | ۷ فهرست سیاه سراسری، ۱۱ شمارهٔ غیرفعال |

**انتشار عمومی:** شرطش این بود که هیچ شکافی باز نماند. حالا نمانده، پس از
این نظر آماده است. تصمیم دربارهٔ خودِ انتشار جداست.
