# مرجع وب‌سرویس پیامکی پیام‌رسان

توصیف ماشین‌خوان رابط برنامه‌نویسی سامانهٔ پیامکی
[پیام‌رسان](https://payam-resan.com).

این مخزن **منبع حقیقت** است. مستندات `docs.payam-resan.com`، نمونه‌کدهای هر
زبان و سرور MCP همگی از همین‌جا مشتق می‌شوند. هیچ‌کدام نباید دستی با سرویس
هم‌گام شوند، چون در آن حالت هر تغییر API یعنی ده‌ها ویرایش پراکنده و
واگرایی خاموش.

## چیدمان

```
specs/
└── v3/
    ├── openapi.yaml              توصیف OpenAPI 3.1
    └── codes/
        ├── error-codes.yaml      مقادیر ErrorCode
        ├── status-codes.yaml     مقادیر StatusCode
        └── template-status.yaml  وضعیت تأیید قالب
scripts/
└── validate.py                   spec در برابر جدول‌ها
```

نسخه یک پوشه است، نه یک شاخه و نه یک تگ. نسخه‌های قدیمی‌تر سرویس هنوز فعال‌اند
و باید در کنار نسخهٔ جاری خوانده شوند، پس هر نسخه پوشهٔ خودش را می‌گیرد و
اعتبارسنج همه را با هم بررسی می‌کند. اضافه شدن یک نسخه یعنی یک پوشهٔ تازه و
هیچ تغییری در پوشه‌های موجود.

## چرا کدها جدا از spec

مقادیر `ErrorCode` و `StatusCode` در دو جا لازم‌اند: به‌عنوان `enum` در
اسکیمای پاسخ، و به‌عنوان جدولِ «این عدد یعنی چه» که مستندات، نمونه‌کدها و
سرور MCP نشان می‌دهند. یکی‌شان بدون دیگری کافی نیست، و نگه داشتن متن فارسی
داخل `description` یک enum عملاً غیرقابل مصرف است.

پس عددها در spec می‌مانند، متن‌ها در `codes/`، و
[`scripts/validate.py`](scripts/validate.py) شکست می‌خورد اگر این دو از هم
واگرا شوند.

## اجرا

دو بررسی مستقل، و هر دو باید سبز باشند.

**۱. سازگاری spec با جدول کدها** — تنها وابستگی `PyYAML` است.

```bash
python3 scripts/validate.py            # بررسی و گزارش
python3 scripts/validate.py --gaps     # فقط فهرست شکاف‌ها، برای پیگیری
python3 scripts/validate.py --strict   # هشدار هم شکست حساب می‌شود
```

**۲. اعتبار خود OpenAPI** — با Docker، بدون نصب چیزی.

```bash
docker run --rm -v "$PWD":/spec -w /spec redocly/cli lint specs/v3/openapi.yaml
```

قواعد خاموش‌شده و دلیلشان در [`redocly.yaml`](redocly.yaml) است.

## شکاف‌های شناخته‌شده

اینها در خود سرویس‌اند، نه در این مخزن، و هیچ‌کدام حدسی پر نشده است. هر
کدی که `confirmed` نباشد در `--gaps` می‌آید تا فراموش نشود.

| شکاف | جزئیات | وضعیت |
|---|---|---|
| کدهای خطای بی‌شرح | `16`، `17`، `18`، `19`، `20`، `100` را سرویس اعلام می‌کند ولی فهرست رسمی شرحشان نمی‌دهد | باز |
| کد خطای بی‌اعلام | `7` («ایمیل تأیید نشده») مستند است ولی در `enum` سرویس نیست | باز |
| وضعیت‌های بی‌شرح | `18` تا `21` را سرویس اعلام می‌کند ولی فهرست رسمی شرحشان نمی‌دهد | باز |
| وضعیت قالب | مقدار `0` واقعی است ولی `enum` سرویس جا انداخته؛ اصلاح سمت سرویس لازم است | معنی روشن شد |
| غلط املایی در پاسخ | فیلد فرستنده در `GetInbox` نامش `Form` است، نه `From` | پذیرفته، عیناً ثبت شد |

دو متد هم هستند که سرویس ارائه می‌دهد و فهرست رسمی اصلاً نامشان را نمی‌برد:
`GetInbox` و واریانت `POST` متد `SendTokenSingle`. هر دو اینجا مستند شده‌اند.

**پیش‌شرط انتشار عمومی:** تا وقتی ستون «وضعیت» ردیف بازی دارد، این spec
منتشر نمی‌شود. شکاف‌ها اول از سمت پنل پیگیری و بسته می‌شوند.
